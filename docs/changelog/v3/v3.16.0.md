# Slothlet v3.16.0 Changelog

**Release Date**: September 2026
**Release Type**: Minor
**Branch**: `release/3.16.0`

---

## Overview

Version 3.16.0 adds **stackable lifecycle routines** (#341): a `routines` config option that stacks every module's contribution to a named lifecycle-hook-style export (`initialize`, `shutdown`, or any custom name) into one callable at its composed api path, plus a root cascade (`self.<name>()` ≡ `api.slothlet.<name>()`) that runs every matching contribution anywhere in the tree. Slothlet's ordinary recursive-merge silently kept only the first writer whenever two or more modules exported the same key at the same path — correct for regular leaves, wrong for a hook every contributing module wants to run.

This replaces the internal `_collectLifecycleHooks` walk entirely — the mechanism behind the now-deprecated `collectLifecycleHooks` option — with one general-purpose system that covers `shutdown`/`destroy` auto-invocation (its old job) plus arbitrary named routines, startup invocation, and multi-contributor stacking (both new).

No public API is removed and no existing behavior changes unless a project opts in — either by setting `routines` explicitly, or by turning on `autoRoutines`/`collectLifecycleHooks`. See **Deprecations** below for one non-obvious behavior change that _does_ apply automatically to existing `collectLifecycleHooks: true` consumers.

Also closes out the live runtime's remaining unpinned deferred-callback boundaries: `requestAnimationFrame`/`cancelAnimationFrame`, `requestIdleCallback`/`cancelIdleCallback`, IDL `on*` handler properties on `EventSource`/`WebSocket`/`Worker`/`MessagePort`/`FileReader`/`XMLHttpRequest`, and the `MutationObserver`/`ResizeObserver`/`IntersectionObserver` constructors are now all identity-pinned the same way `setTimeout` and `EventTarget.addEventListener` already were — see **Bug Fixes** below.

## 🐛 Bug Fixes

### `requestAnimationFrame` pinned in scheduler-context boundary patching (#349, #350)

`enableSchedulerPatching()` patched `setTimeout`, `setInterval`, `setImmediate`, `queueMicrotask`, and `process.nextTick` to pin the calling module's identity at scheduling time and restore it when the callback runs, but not `requestAnimationFrame`. A live-runtime browser-mode module that deferred its first `self`/`context` touch into an `rAF` callback — a common layout-thrash-avoidance pattern — got no identity restored and hit `RUNTIME_NO_ACTIVE_CONTEXT_SELF`, the same failure the timer patches exist to prevent for `setTimeout`. `requestAnimationFrame` is now added to `enableSchedulerPatching()`'s entry points, guarded for host absence the same way `setImmediate`/`process.nextTick` already are; `cancelAnimationFrame` needs no wrapper of its own since its handle passes straight back untouched, matching how `clearTimeout`/`clearInterval` already work off a patched `setTimeout`/`setInterval` handle. Fixed in #350 (from #349).

### `requestIdleCallback`, IDL `on*` handler properties, and Observer constructors pinned (#352, #353)

A follow-up audit of every place a live-runtime callback can be scheduled without going through a patched boundary turned up three more gaps, each a different shape:

- **`requestIdleCallback`/`cancelIdleCallback`** — same bucket as `requestAnimationFrame`; added to `enableSchedulerPatching()` with the identical guard-for-absence and handle-passthrough treatment.
- **IDL `on*` handler properties** — `eventtarget-context.mjs` only patched the `addEventListener` method; assigning `thing.onmessage = fn` writes straight to the interface's own accessor and bypassed it entirely. Since there's no single `EventTarget.prototype.onX` (each interface declares its own `on*` attributes independently), a new `src/lib/helpers/eventtarget-property-context.mjs` patches each interface's on* accessor by name — `EventSource`, `WebSocket`, `Worker`/`MessagePort`, `FileReader`, `XMLHttpRequest` — tracking the pinned wrapper per target in a `WeakMap` so the getter still returns the exact function assigned. `HTMLElement`'s `on*` attributes (`onclick`, …) are deliberately left unpatched since `addEventListener` already covers DOM listener registration.
- **Observer constructors** — `MutationObserver`/`ResizeObserver`/`IntersectionObserver` take their callback as a constructor argument, a third boundary shape neither existing patch covered. A new `src/lib/helpers/observer-context.mjs` wraps all three constructors with `Reflect.construct` so the callback is pinned before construction, while `instanceof`, subclassing, and static extras keep working the same as unpatched; the wrapper constructor gets its own prototype linked to the original's rather than sharing it verbatim, so `instance.constructor` reflects the patched global instead of the unpatched original.

Hardening from review: `wrapperSet` (the on\* property patch) now mutates its tracked `WeakMap` entry only after the platform setter succeeds, so a throwing assignment can't leave the tracked entry out of sync with what's actually installed, and `wrapperGet` deletes the tracked entry when the platform no longer reports the wrapper it installed rather than leaving a stale pair reachable for the target's lifetime; a non-configurable on\* accessor is now skipped instead of aborting the whole patching pass. Fixed in #353 (from #352).

## ✨ Features

### Stackable lifecycle routines (#341)

- **Config**: `routines: Array<string | { name, mode?, recursive?, order? }>`. String forms: `"name"` (mode `"manual"`) or `"name:mode"`. Object form adds `recursive` (boolean, default `false`) and `order` (`"mount" | "depth"`, mode-defaulted). Providing `routines` at all **replaces** the built-in default (`slothlet.defaults.routines`: `initialize` → `startup`, `shutdown` → `shutdown`) — spread `slothlet.defaults.routines` to extend rather than replace, or pass `[]` to disable every routine. A routine name may not be `"slothlet"` or a prototype-pollution meta-key (`__proto__`, `constructor`, `prototype`) — both are rejected at config-validation time, since a routine's name is used verbatim as a property key on the api root and `api.slothlet`.
- **Name matching — three modes, all reusing slothlet's existing glob engine (`compilePattern()`)**:
  - **Bare / dotted, mount-relative (default)** — `name` is resolved relative to the module's own mount point (a `dir`-scan top level, or an `api.add()` target). A bare name (`"initialize"`) matches only that mount's own top level; a dotted name (`"admin.initialize"`) matches a fixed relative sub-path. A mount's own top level is always eagerly constructed regardless of lazy/eager mode, so the common case never forces materialization.
  - **`recursive: true`** — the dotted/bare name is searched at _any_ depth within the mount's own subtree (`**.<name>` under the mount), not just the fixed relative path — including a subtree whose own top-level folder happens to be literally named `shutdown`, `destroy`, or `slothlet`, since those names are reserved only at the true api root, never at a mount's own top level.
  - **`^`-prefixed, root-anchored** — the name is a full glob (`*`, `**`, `{a,b}`, `!`) matched against the complete composed api path, crossing mount boundaries (e.g. `^ext.*.initialize`, `^**.shutdown`).
  - Recursive and root-anchored matches force lazy-mode materialization of the relevant subtree (the whole tree, for a root-anchored pattern) before a cascade runs — the deliberate, unavoidable crux of combining lazy mode with a routine name that isn't mount-top-level. That materialization is scoped to what the pattern actually needs: when a mount's contents are already covered by the base compose's own subtree, they aren't walked a second time.
- **Modes**: `manual` (never auto-runs; always stacked/callable), `startup` (cascade runs once, at the end of `load()` / `await slothlet(...)`), `shutdown` (cascade runs on `api.shutdown()` / `api.slothlet.shutdown()`), `destroy` (cascade runs on `api.destroy()`, which also runs the root `shutdown()` afterward — so a `mode: "shutdown"` routine still runs as part of `destroy()` too; `destroy` covers only what a consumer wants to fire specifically on destroy). `destroy()`'s own teardown (marking the instance destroyed, clearing api keys, nulling `slothlet.api`) always completes even when a routine fails during either its `destroy`-mode cascade or the `shutdown()` call it makes internally — any failure is deferred and rethrown only after cleanup finishes.
- **Root cascade ordering**: `order: "mount"` (default for `startup`/`manual`) runs groups in registration order; `order: "depth"` (default for `shutdown`/`destroy`) runs deepest composed-path groups first, mirroring the old walk's deepest-first teardown order.
- **Errors — best-effort, aggregated**: a throwing contributor does not stop the chain — every contributor at a path, and every path in a cascade, still runs, and a receiver that can't be resolved (e.g. a permission-gated read) is treated like a missing one rather than aborting the run. If any contributor failed, one aggregated `ROUTINE_FAILED` error is thrown afterward (`context.count`, `context.failures: [{apiPath, moduleID}, …]`, `cause` = the first failure) — matching `module-manager.mjs`'s existing best-effort convention rather than introducing a second error-handling philosophy.
- **De-duplication and re-mount safety**: a module's contribution is captured once per `(apiPath, moduleID)` regardless of how many `impl:created`/`impl:changed` events it produces; removing a module drops its contributions from every affected cascade without double-counting a re-add.
- **`autoRoutines`** (new, non-deprecated replacement for `collectLifecycleHooks`): `false` by default (temporary v3-compat — see Deprecations). Every configured routine is always stacked and directly callable regardless of this flag; `autoRoutines` only gates _automatic_ firing (`startup` at compose end, `shutdown`/`destroy` at dispose).
- **`slothlet.defaults`**: new public namespace (attached on both the ESM and CJS entry points) exposing `slothlet.defaults.routines` (the frozen built-in routines list) and `slothlet.defaults.reservedExports` (the framework-reserved export names, as a genuinely immutable `Set` — reads work normally but `add`/`delete`/`clear` throw, since `Object.freeze()` alone doesn't stop a `Set`'s own mutating methods) — lets a consumer extend the defaults without retyping them.

## ⚠️ Deprecations

### `collectLifecycleHooks` — deprecated in favor of `routines` + `autoRoutines`

`collectLifecycleHooks` (and its internal engine, `_collectLifecycleHooks`) is removed and fully replaced by the routines system. Setting `collectLifecycleHooks: true` now:

1. Expands into two implicit, root-anchored routines reproducing the old option's exact scope for literally-named hooks: `{ name: "^**.shutdown", mode: "shutdown", order: "depth" }` and the `destroy` equivalent — whole-tree, cross-mount, deepest-first, best-effort, same as the original walk.
2. **Drops** any existing `shutdown`/`destroy`-mode routine already in the effective list — including the built-in default `shutdown` routine — before adding the two implicit ones, so a contributor is never invoked twice (once via the default bare-name routine, once via the implicit root-anchored one).
3. Sets the effective `autoRoutines` to `true`, unless `autoRoutines` is given explicitly (which always wins).

A project that only ever used `collectLifecycleHooks: true` for its documented purpose (auto-invoking nested `shutdown`/`destroy` functions) sees identical behavior for those two hooks. Emits a `V3_CONFIG_DEPRECATED` warning unless `silent: true`; will be removed in v4.

**Compatibility note — `autoRoutines` is not per-mode.** Because `collectLifecycleHooks: true` now also sets `autoRoutines: true`, and the built-in default routines list includes `initialize` (mode `startup`) alongside `shutdown`, turning on `collectLifecycleHooks` also newly auto-invokes any top-level `initialize` export at every mount's own root at the end of compose — something the old mechanism never did (it only ever touched `shutdown`/`destroy`). A project with `collectLifecycleHooks: true` and a mount-root `initialize.mjs` that was previously just an inert leaf will now have that function called automatically on `await slothlet(...)`. This is a side effect of `autoRoutines` being a single all-modes gate rather than a per-mode one, not a bug — but it is a real, non-obvious behavior change for existing `collectLifecycleHooks: true` consumers who happen to have a top-level `initialize` export they did not intend as a startup hook. (Nested/non-top-level `initialize` exports are unaffected — the default `initialize` routine is bare and mount-relative, not recursive or root-anchored.)

**Migration recipe for v4 (once `collectLifecycleHooks` is removed)** — reproduce the exact same effect explicitly:

```js
await slothlet({
	dir: "./api",
	autoRoutines: true,
	routines: [
		...slothlet.defaults.routines, // keep initialize:startup, drop or override as needed
		{ name: "^**.shutdown", mode: "shutdown", order: "depth" },
		{ name: "^**.destroy", mode: "destroy", order: "depth" }
	]
});
```

If the newly-surfaced `initialize` auto-invocation described above is unwanted, drop it from the spread (`routines: [{ name: "shutdown", mode: "manual" }, { name: "^**.shutdown", ... }, { name: "^**.destroy", ... }]` — keep `initialize` `manual` or omit it) while keeping `autoRoutines: true` for the shutdown/destroy cascades.

## ⚠️ Known Limitations

The per-path stacked callable (as opposed to the root cascade, which always force-materializes what it needs and re-reads current state on every call) is only (re)installed at three points: the end of the initial compose, after every `api.add()`, and immediately before an auto-fired `startup`/`shutdown`/`destroy` cascade runs. An ordinary property touch or a late direct `self.x.y = fn` reassignment is captured into the routine registry either way — that part is never missed — but neither one re-triggers a rebuild. For the common case of a single contributor at a path this is invisible, since first touch resolves to that one function whether or not it's been (re)stacked. It's only an observable gap when **two or more contributors collide on the exact same composed api path** and the second one is captured after the last rebuild already ran (a late reassignment, or a second lazy mount whose leaf stays untouched at `api.add()` time): the property then reflects only the plain merge winner, silently dropping the other contributor, until an unrelated later event re-triggers a rebuild and folds it in. Tracked in #362.

## Upgrade notes

- **No breaking changes.** `routines` and `autoRoutines` are both opt-in (`autoRoutines` defaults to `false`); a project that never touches either sees no behavior change, including the built-in default `initialize`/`shutdown` routines — they are always stacked/callable but never auto-fire unless `autoRoutines: true`.
- **`collectLifecycleHooks: true` now also implies `autoRoutines: true`** (unless `autoRoutines` is set explicitly) — see Deprecations above for the resulting `initialize` auto-invocation side effect. This is the one case existing consumers of the deprecated flag should specifically check for.
- **`collectLifecycleHooks` is deprecated**, emits `V3_CONFIG_DEPRECATED` unless `silent: true`, and will be removed in v4 — see the migration recipe above.
- **The boundary-patch fixes are also non-breaking and drop-in.** A live-runtime browser-mode module that schedules deferred work via `requestAnimationFrame`/`requestIdleCallback`, assigns an IDL `on*` handler property, or constructs a `MutationObserver`/`ResizeObserver`/`IntersectionObserver` now gets correct `self`/context identity inside that callback where it previously threw `RUNTIME_NO_ACTIVE_CONTEXT_SELF` or silently ran unattributed; no code changes are required to pick this up.
