# Slothlet v3.20.0 Changelog

**Release Date**: September 2026
**Release Type**: Minor
**Branch**: `release/3.20.0`

---

## Overview

Version 3.20.0 extends permission-rule **function conditions** so they can gate on the resource named in the call itself, not just ambient context. A function condition now receives a second argument alongside the runtime context — `condition(ctx, { args, target })` — carrying the invocation's own arguments and the concrete (post-glob) target api path. This makes a _resource-scoped_ gate declarative: a rule can decide "may this caller read the project whose id is `args[0]`" on the leaf itself, instead of every call site having to inject the resource id into the runtime context via `context.run()`.

The change is purely additive and backward-compatible. Existing one-argument conditions keep working unchanged, object and array conditions are unaffected, and because an args-reading condition is still a condition-bearing rule it already bypasses the decision cache — no cache behavior changed. Conditions remain fail-closed on throw, so a predicate that reads `callMeta.args` must guard for the metadata's absence off the call path.

## ✨ Features

### Resource-scoped condition gates — `condition(ctx, { args, target })` (#455)

Permission-rule function conditions previously saw only the per-request runtime context, `condition(ctx)`, so they could express a context-level gate (`(ctx) => ctx.role === "admin"`) but not a resource-scoped one — the resource being acted on is a _call argument_, not ambient context. v3.20.0 threads a `callMeta` object into the condition as its second argument:

- **`callMeta.args`** — the arguments the target leaf was called or constructed with.
- **`callMeta.target`** — the concrete (post-glob) target api path, so a single `**`-globbed rule can branch on exactly which leaf was invoked.

```javascript
// Authorize on the resource identified in the call itself — no ceremony at the call site:
{ caller: "**", target: "project.get", effect: "allow",
  condition: (ctx, { args }) => hasRole(ctx.caller, args[0], "read") }

await self.project.get(projectId); // the id is the call arg the condition already sees
```

- **Where it is provided:** the **call** gate (`self.x.leaf(...)`), the **construct** gate (`new self.x.Foo(...)`), and a **captured reference** invoked later (`const f = self.x.leaf; f(...)`) — all three see the invocation's real arguments. `callMeta` is **`null`** everywhere else a condition is evaluated: terminal-value reads, hook gating, event delivery, the internal `slothlet.*` control surface, and silent queries (`permissions.global.checkAccess`, `permissions.self.access`, `matchesCondition`). Write `callMeta`-reading conditions defensively (`(ctx, meta) => meta?.args?.[0] === id`) — a throw is caught and treated as a non-match, never an implicit allow.
- **Additive & backward-compatible:** existing `condition(ctx)` functions ignore the extra argument; plain-object and array conditions are unchanged (only the function branch forwards `callMeta`). No cache changes — an args-reading condition is a condition-bearing rule, which already bypasses the path-pair decision cache.
- This is the declarative replacement for hand-rolled per-resource wrappers (a `GATE` map plus a `_leaf` wrapper reading `args[0]`): the mechanism is slothlet's enforcement, the identity is injected by the host via `context.run({ caller })`, and the predicate is supplied by the application. Implemented in [#456](https://github.com/CLDMV/slothlet/pull/456).

See the new **Second argument: call metadata** and **Resource-Scoped Gates** sections in [docs/PERMISSIONS-CONDITIONS.md](../../PERMISSIONS-CONDITIONS.md).

## Upgrade notes

A drop-in for v3.19.x. The `callMeta` second argument is additive — existing one-argument conditions (`(ctx) => …`) and object/array conditions behave exactly as before; adopt `condition(ctx, { args, target })` only where you want a resource-scoped gate. Because `callMeta` is `null` off the call/construct path, guard any `callMeta.args` access (`meta?.args?.[0]`) so a rule that also matches a read/hook/event target stays fail-closed rather than throwing.
