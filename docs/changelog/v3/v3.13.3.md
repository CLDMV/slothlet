# Slothlet v3.13.3 Changelog

**Release Date**: August 2026
**Release Type**: Patch
**Branch**: `release/3.13.3`

---

## Overview

Version 3.13.3 finishes the composition fix started in 3.13.2 and closes a separate multi-instance permission hole. 3.13.2 (#284) stopped the module-private (`_`/`__`) rule from denying slothlet's own version-dispatcher marker keys on the collision-merge read path, but a permissions-enabled consumer could still fail to boot: a **second** framework read path — the post-`api.add` materialization drain and the load-time detection walks — probed the marker through a gated `__`-private read on whatever data leaf it was walking, so under `private.host: deny` that read was refused with `PERMISSION_DENIED` (#287). Those walks now recognize a version dispatcher by object identity (the module-private brand) instead of reading `__isVersionDispatcher`, so no gated read happens; a data field such as `activationEvents` remains a legitimate version-dispatch target — only the framework's _detection_ of a dispatcher changed.

Separately, a second `slothlet()` created from inside a leaf of a first, permissioned instance was denied during its own boot (#290): the context managers are process-wide singletons, so enforcement for the nested instance read the ambient caller from the outer instance's flow. Enforcement now resolves the caller and store from the instance doing the enforcing, so a nested boot behaves exactly like a standalone one, upholding the documented Multi-Instance Isolation contract. No public API changed, and there are no breaking changes.

## 🐛 Bug Fixes

### Version-dispatcher marker still denied via a second framework read path (#287)

3.13.2 (#283/#284) exempted the framework's own reads of its version-dispatcher marker keys (`__isVersionDispatcher`, `__logicalPath`) from the 3.13.0 module-private rule (#269) by keying the exemption on a module-private brand — but only on the path where a version-dispatched field collides with an existing module and its markers are merged onto that module's wrapper. A permissions-enabled consumer could still fail to boot because a second framework path reads the marker: the post-`api.add` materialization drain (`collectPendingMaterializations`) and the load-time dispatcher-detection walks call `getOwnPropertyDescriptor`/read the property on each node they traverse, and on a version-dispatched **data** leaf that meant a `__`-private read (for example `manifest.activationEvents.__isVersionDispatcher`). Under the secure-default `private.host: deny` policy that read was refused with `PERMISSION_DENIED`, aborting the mount.

The walks now detect a version dispatcher by **object identity** — the same module-private brand 3.13.2 introduced — rather than by reading `__isVersionDispatcher`. Because the brand is checked instead of a property being read, the read gate is never engaged, so a dispatcher is skipped without a gated access regardless of which data key it is stamped on. A version-dispatched data field such as `activationEvents` is still a legitimate dispatch target whose value can differ per version; only the framework's detection of "is this node a dispatcher" changed from a gated read to a brand check. A consumer that merely exports a member named `__isVersionDispatcher` is unaffected, because detection keys on identity, never on the name.

**Lazy materialization drain now covers function-typed wrappers.** The post-`api.add` drain excluded function-typed values, but an unmaterialized lazy `UnifiedWrapper` is `typeof === "function"` until it resolves — so the drain skipped every lazy wrapper and its in-flight `materializationPromise`, making it a no-op in exactly the mode (lazy) it exists for. It now admits function-typed wrappers and, after walking a wrapper's raw children, returns without also enumerating the proxy (which would trip its `ownKeys` trap and eagerly materialize the very wrappers lazy mode defers) — mirroring `Slothlet._drainInFlightLoads`.

### Nested slothlet instance denied during its own boot inside a permissioned instance (#290)

Creating a second `slothlet()` from inside a leaf of a first, permissioned instance threw `PERMISSION_DENIED` on the nested instance's own `slothlet.*` internals (for example `slothlet.permissions.control.enabled`) during its construction. The live and async context managers are process-wide singletons shared by every instance, so when the nested instance's own boot introspected its api tree, enforcement resolved the "current caller" from the globally-active flow — which at that moment was the outer leaf executing `await slothlet(...)`. The outer caller is not a caller of the nested instance, so denying its construction against that identity contradicts the documented Multi-Instance Isolation guarantee. Booting the same nested instance standalone always worked; the bug needed the outer instance to have set an ambient caller.

Enforcement now resolves both the context store and the caller identity from the **enforcing instance's own** store: `tryGetContext()` and `getCallerIdentity()` take an optional instance id, and the three enforcement sites (`enforceInternalPermission`, `canTraverseInternalNamespace`, and the `UnifiedWrapper` read gate) pass their own instance's id. A flow belonging to a different instance is invisible to enforcement, so a nested instance under construction resolves no ambient caller from its own fresh store and proceeds exactly as a standalone boot does. Crucially, this scopes the _store lookup_ rather than nulling the caller outright, so a concurrent sibling whose call is parked at an `await` — while the shared global momentarily points at another instance — is still resolved from its own store and enforced. Same-instance behavior is byte-for-byte unchanged.

## 🧪 Tests

- **Nested-boot isolation regression (#290)** — `tests/vitests/suites/isolation/nested-instance-boot.test.vitest.mjs` boots an unpermissioned and a default-deny nested instance from inside a leaf of a permissioned outer instance, across the async/live × eager/lazy matrix, and asserts the nested boot no longer throws and its leaves resolve. Fixtures under `api_tests/api_test_nested_isolation/` supply the outer leaf that boots the nested instance with the outer's runtime.
- **Shared-wrapper drain dedup (#287)** — `tests/vitests/suites/api-manager/api-add-shared-wrapper-drain.test.vitest.mjs` aliases one existing api wrapper at two positions in a single synthetic `api.add`, so the post-add drain reaches the same wrapper twice and exercises its recursion-dedup guard, asserting both aliases resolve.
- **Dispatcher-detection walks (#287)** — coverage of the brand-based detection on the drain and load-time walks, including a version-dispatched data leaf and the dispatcher-skip path.

The full suite passes and the change holds the coverage gate at 100%.

## Upgrade notes

- **No breaking changes.**
- **Completes the permissions fix for version-dispatched fields.** If you upgraded to 3.13.2 and a permissions-enabled application still failed to mount a version-dispatched (or manifest) field with `PERMISSION_DENIED` on `…__isVersionDispatcher`, 3.13.3 closes the remaining read path — no consumer-side change required.
- **Fixes nested `slothlet()` under permissions.** Booting a second instance from inside a leaf of a permissioned instance — the documented multi-instance pattern — no longer throws during the nested instance's own construction.
