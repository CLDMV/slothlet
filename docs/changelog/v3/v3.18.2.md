## Overview

Version 3.18.2 is a **CI / release-automation-only** release — no runtime or package code changed, and the published package is functionally identical to v3.18.1. It fixes the mechanism that re-evaluates the persistent `next → master` release PR so a green, approved release actually converges to a merge instead of stalling.

The release-merge check was triggered by `check_suite: completed`, but GitHub does not deliver that event for a check suite created by GitHub Actions itself — which is every check this repo's own `ci.yml` produces (coverage badge and PR-comment jobs included); it fires only for a check suite created by a third-party App. So once a release PR's initial evaluation ran while coverage was still in flight, nothing re-fired when CI finished, and a fully-green, approved release PR could sit for 20+ minutes with no re-trigger.

---

## 🔧 CI & tooling

### Re-arm the release-merge re-evaluation via `workflow_run` instead of `check_suite` (#439)

`release-merge.yml`'s trigger is switched from `check_suite: completed` to `workflow_run` on `ci.yml` (named by its literal workflow name, which `workflow_run` matches on — it cannot be templated). `workflow_run` is GitHub's documented mechanism for "re-run something when this other workflow finishes" and does not have the Actions-authored-check-suite restriction, so the release PR re-evaluates reliably the moment CI completes. The reusable `CLDMV/.github` workflow threads `workflow_run.head_branch` through as the primary source (falling back to `check_suite.head_branch`), so no consumer-side resolution logic changed — this repo only swapped the trigger. Underlying cause tracked in CLDMV/.github#318.
