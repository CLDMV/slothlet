# Slothlet v3.16.1 Changelog

**Release Date**: September 2026
**Release Type**: Patch
**Branch**: `release/3.16.1`

---

## Overview

Version 3.16.1 is a single-fix patch that widens the optional `typescript` peer dependency so downstream consumers can adopt TypeScript 7. Slothlet's shipped type declarations were already TypeScript 7-compatible; the peer range simply hadn't been opened up, which blocked those consumers' installs. No runtime code changed — this is a drop-in for v3.16.0.

---

## 🐛 Bug Fixes

### `typescript` optional peer widened to allow TypeScript 7 (#382)

The optional `typescript` peer was pinned to `^6.0.3`. Because `npm ci` enforces peer ranges strictly even for `optional` peers, any consumer that carries `@cldmv/slothlet` and bumped its own `typescript` devDependency to `^7` hit a hard `ERESOLVE` install failure — `peerOptional typescript@"^6.0.3" from @cldmv/slothlet` against `typescript@7.x` — regardless of the peer being optional. That blocked every such consumer's Dependabot bump to TypeScript 7, not only the one where it first surfaced (CLDMV/droidsock#35).

The peer is now `^6.0.3 || ^7.0.0`. This was verified rather than assumed: slothlet's shipped `.d.ts` validate cleanly under TypeScript 7.0.2 across all 42 published export paths, so a TypeScript 7 consumer can install `@cldmv/slothlet` and type-check against its declarations with no errors.

slothlet's own dev toolchain intentionally stays on TypeScript 6 (`devDependencies.typescript` remains `^6.0.3`): TypeScript 7's declaration emitter regresses on slothlet's function-typed JSDoc typedef members — it drops the property name and emits a bare `: Function;` that then fails to re-parse — so slothlet's internal `build:types` cannot run under TypeScript 7 yet. That is an emit-side limitation of slothlet's own build only; it has no bearing on consuming the shipped types under TypeScript 7.
