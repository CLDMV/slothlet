# Slothlet v3.15.2 Changelog

**Release Date**: September 2026
**Release Type**: Patch
**Branch**: `release/3.15.2`

---

## Overview

Version 3.15.2 is a **bug-fix release for the core context/composition runtime**. It closes several long-standing gaps where documented behavior didn't actually hold — class-instance context propagation from `async` leaves, writable `self.X = <object>` wrap-on-set, and `api.slothlet.api.add()` on objects carrying native handles — and fixes a process-wide memory leak in the global EventEmitter context patch that affected long-lived services.

No public API changed and there are no breaking changes; this is a drop-in for 3.15.1. Everything here is a case of something that was supposed to work now working: async factory leaves keep their `self`, wrap-on-set objects get the same wrapping (and permission gating) as `add()`, `add()` no longer hangs on a mounted socket, and the EventEmitter patch no longer pins emitters in memory. Coverage is restored to 100% with regression tests for each fix (#334).

---

## 🐛 Bug Fixes

### Class-instance context propagation now fires for async leaves (#328)

`AsyncContextManager.runInContext()` decided whether to apply class-instance context wrapping by checking the _synchronous_ return of `fn.apply(...)`. For any `async function` leaf that return is always a pending `Promise` — which is itself in the excluded-constructors list — so the documented "Class Instance Context Propagation" never applied to async leaves. `await api.mod.create()` (an async factory returning a class instance) resolved to an **unwrapped** instance, and a later method call that used `self` threw `RUNTIME_NO_ACTIVE_CONTEXT_SELF`. The resolved value of an async leaf is now wrapped, so essentially every real-world async factory (connect, read-config, open-handle) gets the context propagation the docs describe. Fixed in #331.

### Wrap-on-set `self.X = <object>` applies `add()`-equivalent wrapping (#329)

`docs/CONTEXT-PROPAGATION.md` describes assigning a function or object to an owned `self.X` path as receiving "the same wrapper construction `api.slothlet.api.add()` uses." In practice the set trap stored the assigned value **raw**, with two consequences: an assigned object's methods ran outside any context-preserving wrapper (a later `self.*` access threw `RUNTIME_NO_ACTIVE_CONTEXT_SELF`), and a pure-data object's terminal values bypassed permission read-gating entirely. Assigned objects and functions now get the full wrapper treatment: methods resolve cross-module `self` (at any nesting depth), and pure-data terminals are permission-checkable identically to `add()`-mounted data. The wrapping is applied lazily one level per access, so an arbitrarily deep runtime-grafted chain no longer overflows the stack, and `reload()` preserves these user-assigned overrides verbatim. Fixed in #333.

### `api.slothlet.api.add()` no longer hangs on a socket or circular value (#330)

Mounting an object whose property was a live `net.Socket` — or any `EventEmitter`, stream, or self-referential native value — made `add()` hang forever with no error. The synthetic flatten/wrap walk treated such a value as a descendable namespace and recursed its deep, circular internal graph (`_handle`, `_readableState`, `_events`, …) with no cycle guard, blocking the event loop so completely that a caller's own timeout could never fire. EventEmitters (and the rest of the opaque class-instance category) are now treated as opaque leaf data and preserved by reference, and an ancestor-scoped cycle guard — tracking both objects and callable namespaces — makes any circular graph fail-fast instead of hanging. Fixed in #332.

### Global EventEmitter context patch no longer leaks emitters (#335)

To preserve `AsyncLocalStorage` context across event callbacks, slothlet patches `EventEmitter.prototype` process-wide and tracked wrapped listeners in a **strong-keyed `Map`**. Because the patch applies to _every_ emitter in the process — including Node's own `http.IncomingMessage`/`ServerResponse`, sockets, and streams, which attach listeners that are never explicitly removed and normally just ride the object into garbage collection — the strong Map key pinned each such emitter (and everything reachable from it) for the life of the process. Long-lived services saw steady, unbounded RSS growth (~11.5 KB per request, ~200–300 MB/hour in a Fastify service, heap-snapshot root-caused). The tracking map is now a `WeakMap`, so an emitter with no other referrers is collected normally — listeners and all — exactly like unpatched Node; shutdown additionally drops the tracked framework-owned emitters' entries explicitly. Fixed in #336.

## 🧪 Tests & coverage

- **Regression coverage restored to 100% (#334)** — added regression tests covering each of the above: async-leaf class-instance `self`, deep-nested wrap-on-set `self`, wrap-on-set permission read-gating parity with `add()`, callable-namespace indirect cycles, and reload/collision-merge preservation of user-assigned overrides. Lines, statements, functions, and branches are all back to 100%.

## Upgrade notes

- **No breaking changes — drop-in for 3.15.1.** Every change is a fix to behavior that was already meant to hold, so there is nothing to adjust on upgrade. If your code previously worked around any of these gaps — mounting handle-bearing objects via a post-`add()` property assignment (#330), returning class instances only from _synchronous_ leaves (#328), or avoiding wrap-on-set for objects that need `self` or permission gating (#329) — those workarounds are no longer necessary, though they remain harmless.
- **Long-running services should upgrade** to pick up the EventEmitter listener-tracking leak fix (#335); no code change is required to benefit.
